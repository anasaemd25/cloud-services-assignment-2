Compare application containers to microservices

Microservices and containers are two different things, but people often get them mixed up because they are used together. Microservices are an architectural software design where a big application is broken into smaller independent services, like having one separate service just for user login, another for processing payments, and another for rendering the UI.

Containers, on the other hand, are an isolated process and a deployment technology used to package software. A container bundles code, libraries, dependencies, and runtime environment into a single unit so it runs identically anywhere.

The main difference is that microservices are about how software architecture is designed, while containers are about how software is packaged and deployed. Microservices are a design paradigm, and containers are just the most popular tool to implement that paradigm. However, microservices can exist without containers they can also run on serverless functions, traditional virtual machines, or directly on a host OS. Containers are simply preferred because of fast boot times, resource efficiency, and easy scaling with orchestrators like Kubernetes.

Describe shortly what is Kubernetes and what alternatives are there?

Kubernetes is an open-source container orchestration platform used to automate the deployment, scaling, and management of containerized applications across a cluster of nodes. Managing a single container manually with simple commands is easy, but managing dozens or hundreds in production requires an orchestrator to handle automation tasks like self-healing (restarting crashed containers), rolling updates, load balancing, and auto-scaling when user traffic spikes.

There are several alternatives to standard Kubernetes depending on the use case. Red Hat OpenShift (which powers CSC Rahti) is an enterprise focused platform built on top of Kubernetes that adds extra developer tools and strict security defaults out of the box. Other alternatives include Docker Swarm for lightweight setups, HashiCorp Nomad for managing both containers and non-containerized legacy apps, and cloud-native managed services like AWS.

If you would now use a virtualized Windows operating system in your laptop (whatever operating system the laptop already has): Which virtualization platform (VMware, Virtualbox, Hyper-V, KVM, etc…) would you use and why?

If I had to choose a virtualized Windows operating system and run it on my laptop, I'd probably choose VirtualBox or VMware Workstation. I have used those two platforms for over five years, mainly for setting up Linux distributions like Kali Linux and Parrot OS for learning purposes. Both offer reliable hypervisor virtualization that runs on top of an existing host operating system.

VirtualBox is completely free, open-source, cross-platform, and beginner friendly to configure. VMware is also a very good option because it usually provides a bit better hardware acceleration, 3D graphics support, and overall smooth performance for resource-heavy OS setups like Windows 11 or Windows Server. If I needed a quick free setup I'd use VirtualBox, but for better performance on Windows I'd pick VMware, personally, for basic daily tasks, there's no difference between them for me.

List some information security risks when using third party (for example Docker) containers?

When using third-party container images from public registries (like Docker Hub), several major security risks must be considered:
  • Vulnerabilities in Outdated Base Images: Base images often contain outdated operating system packages or dependencies with unpatched security flaws (CVEs). Attackers can exploit these known vulnerabilities to execute arbitrary code or gain unauthorized access.
  • Malicious Images: Public registries allow almost anyone to upload images. Unverified third-party images could contain hidden malware, crypto-miners, or backdoors designed to compromise the host network.
  • Running as Root (Over-Privileged Execution): Many public container images execute their default processes as the root user. If a security vulnerability allows an attacker to compromise the application, running as root makes container escape attacks much easier, potentially giving the attacker full root access to the host machine.
  • Exposed Secrets in Layers: Developers sometimes accidentally hardcode sensitive credentials, such as database passwords, API tokens, or SSH keys during the build process. Anyone who downloads the container image can inspect its history and extract those.
