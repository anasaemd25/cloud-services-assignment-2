Compare application containers to microservices

Microservices and containers are two different things, but people often get them mixed up because they are used together. Microservices are an architectural software design where a big application is broken into smaller independent services, like having one separate service just for user login, another for processing payments, and another for rendering the UI.

Containers, on the other hand, are an isolated process and a deployment technology used to package software. A container bundles code, libraries, dependencies, and runtime environment into a single unit so it runs identically anywhere.

The main difference is that microservices are about how software architecture is designed, while containers are about how software is packaged and deployed. Microservices are a design paradigm, and containers are just the most popular tool to implement that paradigm. However, microservices can exist without containers they can also run on serverless functions, traditional virtual machines, or directly on a host OS. Containers are simply preferred because of fast boot times, resource efficiency, and easy scaling with orchestrators like Kubernetes.

Describe shortly what is Kubernetes and what alternatives are there?

Kubernetes is an open-source container orchestration platform used to automate the deployment, scaling, and management of containerized applications across a cluster of nodes. Managing a single container manually with simple commands is easy, but managing dozens or hundreds in production requires an orchestrator to handle automation tasks like self-healing (restarting crashed containers), rolling updates, load balancing, and auto-scaling when user traffic spikes.

There are several alternatives to standard Kubernetes depending on the use case. Red Hat OpenShift (which powers CSC Rahti) is an enterprise focused platform built on top of Kubernetes that adds extra developer tools and strict security defaults out of the box. Other alternatives include Docker Swarm for lightweight setups, HashiCorp Nomad for managing both containers and non-containerized legacy apps, and cloud-native managed services like AWS.

If I had to choose a virtualized Windows operating system and run it on my laptop, I'd probably choose VirtualBox or VMware Workstation. List some information security risks when using third party (for example Docker) containers?

When using third-party container images from public registries (like Docker Hub), several major security risks must be considered:
  • Vulnerabilities in Outdated Base Images: Base images often contain outdated operating system packages or dependencies with unpatched security flaws (CVEs). Attackers can exploit these known vulnerabilities to execute arbitrary code or gain unauthorized access.
  • Malicious Images: Public registries allow almost anyone to upload images. Unverified third-party images could contain hidden malware, crypto-miners, or backdoors designed to compromise the host network.
  • Running as Root (Over-Privileged Execution): Many public container images execute their default processes as the root user. If a security vulnerability allows an attacker to compromise the application, running as root makes container escape attacks much easier, potentially giving the attacker full root access to the host machine.
  • Exposed Secrets in Layers: Developers sometimes accidentally hardcode sensitive credentials, such as database passwords, API tokens, or SSH keys during the build process. Anyone who downloads the container image can inspect its history and extract those.

Practical Task Documentation

1. Source Code and Dockerfile Configuration

I created a public GitHub repository named cloud-services-assignment-2 to hold my application code (index.html) and the build instructions (Dockerfile). When deploying to the cloud, you don't install software manually, instead, you write a Dockerfile to tell the platform exactly how to package your app. One major detail I had to handle was the network port, because CSC Rahti has some security rules, so bassicly it runs containers as a standard unprivileged user, not as the "root" admin. Normal web servers usually try to bind to port 80, but normal users aren't allowed to use ports certain ports, which causes a "Permission denied". To solve this, I used the nginxinc/nginx-unprivileged:alpine base image and explicitly told it to listen on port 8080.

2. CSC Project Setup

Before deploying anything, I had to configure my cloud environment using the MyCSC portal under my assigned project. This dashboard is where I manage the project lifetime and enable different cloud resources. For this assignment, I needed to activate three different services: CSC Rahti (the Platform as a Service that will run my container), cPouta (the Infrastructure as a Service virtual machines), and Allas (the object storage service to host my files). You have to explicitly activate these because they are separate environments that consume the project's Billing Units in different ways.

3. Container Deployment on CSC Rahti

This step shows the real benefit of a PaaS platform. Instead of building the container on my own computer, I simply provided the CSC Rahti Web Console with the link to my GitHub repository. Rahti automatically pulled the code, read the Dockerfile, built the image, and deployed it. As seen in the console screenshot, it creates a "Deployment" that manages Pods (the actual running instances of the container). If one of these Pods crashes or is deleted, the orchestrator will automatically spin up a new one to replace it, ensuring the website stays online without me having to fix it manually.

4. Public Application Route

Even though the container is running successfully inside Rahti, it is isolated in an internal network and nobody on the internet can see it yet. To make the website public, I had to create an "edge-TLS Route". This route acts as a bridge, taking public internet traffic and forwarding it securely to my container's internal port 8080. Choosing an edge TLS route is important because Rahti automatically provides a secure certificate for it meaning the website loads over a safe HTTPS connection instead of plain HTTP.

5. Documentation Media Storage in CSC Allas

To host the screenshots for this documentation, I used CSC Allas, which is an object storage service similar to Amazon S3. Unlike a normal computer hard drive with nested folders, object storage keeps data in flat containers called "buckets". I created a bucket named Cloud-Services1, uploaded my images, and set the access rights to public so anyone with the link can view them. This is a much better way to handle media for web pages because object storage is designed to deliver static files quickly over the internet, without taking up space inside the actual web application container.
